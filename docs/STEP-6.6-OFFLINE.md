## Review phase 1: roster persistence

`src/roster-storage.js` owns the single `fc.v2.roster.v1` localStorage record:

- Version, contract, accepted payload and last successful saved synchronization time.
- SHA-256 source binding over endpoint and credential; no second token copy in the record. This is identity binding, not encryption.
- An optional `historyCheckedAt` daily-check timestamp (older version-1 records remain readable without migration). Existing bounded device history (120 days, up to 300 sectors) and server history (up to 2,000 sectors within the backend's 13-month contract).

One `setItem` replaces the complete record. The old record is never deleted before replacement. Both the storage write and readback must succeed. If an update cannot be saved, the existing visible/saved record and last-success time remain unchanged. On first-load write failure, live data can be viewed in memory, but the app states that it is not saved or available offline.

Acceptance is stricter than the display adapters: valid coverage dates and all coverage days, consistent event/sector/duty/window references, non-reversed intervals (including point-in-time events at local midnight), and no malformed legacy entries. Flight sectors still require a positive flight duration under the existing contract. Empty responses and responses unexpectedly dropping all remaining duties are refused. Genuine OFF, leave, standby and other explicitly rostered non-flight events are accepted. Unknown event codes stay unknown. Airport fallback and Local/UTC formatting remain in the established adapters and shared time layer.

A saved v2 roster is not downgraded to the less complete v5 contract when a v2 refresh fails. A saved v5 roster can still refresh through v5 after a v2 failure and upgrade when v2 recovers. Initial v5 fallback remains available for existing legacy backends. Historical merging and cancellation/retiming rules are still owned by the existing history model.

### Migration

On first load with an existing endpoint and token, try legacy caches in descending fetch-time order, selecting the newest **valid** candidate. Preserve its original fetch time; v5 relative fields are never rebased to restart time. Carry over bounded, validated device/server history. Remove the four old cache/history keys only after the new record is saved. On write failure, originals remain and can be displayed conservatively without declaring completed offline setup.

Legacy records were not source-bound; migration necessarily relies on the endpoint/token already configured on that installation. Records with a different source digest, unknown version or corrupted new-format data are never reinterpreted through leftover legacy records. Changing source or token explicitly clears prior-source data. New-format legacy/open-backend records can reopen without a token; old unbound caches without a token are not migrated.

## Review phase 2: static application shell

`sw.js` is generated by `scripts/build-offline.mjs` from `scripts/service-worker.js` and an explicit list of shipped HTML, manifest, JS, CSS and icons. No runtime caching of arbitrary URLs exists.

- Each allowlisted file has a SHA-256 content digest.
- Installation sends same-origin cookies for protected static hosting and verifies every file before completion. Only allowlisted, byte-verified static responses are cached; authentication redirects fail installation. The manifest link explicitly uses credentials so protected Home Screen installation can fetch it.
- Failure removes only that incomplete version; the old worker and cache remain.
- No forced `skipWaiting`: open clients retain their coherent application version.
- Activation keeps the new complete cache and one prior complete cache, without touching unrelated caches.
- On an evicted asset, try the retained previous cache only if its bytes match the active manifest. Otherwise try the network. A changed online response may satisfy the request transiently, but is never inserted into the offline cache. Readiness is rechecked after recovery; a missing entry means incomplete offline setup. This preserves cache integrity, but an online response from a newer build is not proof of runtime compatibility with an older open tab; close old clients and reopen after a complete update.
- Exact allowlisted same-origin GETs and root/index navigation are served from the shell cache. Root query strings such as review mode still use the same static index.
- POSTs, API traffic, personal roster data, credentials, weather, private reference files and arbitrary query-bearing asset URLs are excluded.

`src/offline-shell.js` asks the controlling worker to verify that every required cache entry exists. Registration alone is insufficient. A timed-out worker status query retries at most twice, remaining not-ready until a positive response. The app declares offline readiness only when this check and roster persistence both succeed. Persistent-storage permission is requested as a best effort; refusal is not treated as permission or durability assurance.

After any frontend change, run:

```sh
npm run build
npm run check
npm test
```

The normal test suite fails if the generated worker is stale. A future release must serve the generated worker and its corresponding assets together over HTTPS. Localhost is suitable for desktop verification. Plain HTTP on an iPhone LAN address is unsupported for roster persistence as well as service workers: `crypto.subtle` needs a secure context. `npm run serve` is for desktop localhost; use the approved HTTPS preview on an iPhone. The controller reports this requirement rather than disguising it as a malformed roster.

## Review phase 3: lifecycle, status and deletion

The controller restores saved data before network requests, deduplicates active loads, and refreshes on reconnect. A reconnect arriving during a failed pending request schedules one immediate retry; successful pending requests are not duplicated. Settings → Refresh roster explicitly attempts the network even when `navigator.onLine` is false; automatic requests continue to honor that hint. Existing minute/foreground checks and the ten-minute refresh interval remain. No synchronization is promised while iOS has closed/suspended the app.

Server history remains on a 24-hour policy. Empty or partially adaptable responses preserve the last good history and persist a separate daily-check time. Failed attempts are throttled within the current controller session; a new session may retry a failed request. Neither check time nor failure changes the successful roster synchronization time.

A small status line uses existing typography/colors and is visible on mobile above all screens. It distinguishes saved data, offline mode, refresh failure, authentication failure, storage failure and incomplete offline setup, with an absolute last-success date/time through the shared Local/UTC formatting layer. It does not change duty state or operational certainty.

Sign out replaces the former Remove token action (owner decision D-011, 2026-10-14). It removes the token, the saved roster and histories, the departures cache and weather memory, writes the sign-out marker (revokes other tabs), and removes the account-specific profile fields `name` and `hotelListUrl` (personal saved-hotel-list link). It **keeps** non-sensitive preferences: the operational profile fields (home base(s), home time zone, wake-up offset, airline, no-hotel airports, alarm shortcut name, km per block hour), theme, Local/UTC time display and the endpoint. Disconnect also removes the endpoint. Reset removes every `fc.v2.*` key (credentials, roster, history, all preferences, caches) and returns to initial setup. A token change purges the previous source's roster, histories and departures cache and keeps preferences. Settings explains the difference under the Sign out button and in the Reset description.

If an open/no-token backend starts requiring authentication, its saved roster and histories are purged and a persistent sign-out marker revokes offline access in other tabs and after restart. Credential-bound saved access is retained when a previously configured token expires.

A sign-out marker prevents an open legacy GET from repopulating cleared data. Request generation, source identity and access-revision guards reject late roster/history/departures responses. Settings form requests also have lifecycle guards so delayed connection tests cannot restore credentials after reset/navigation/access changes. Other tabs observe access/reset events and drop personal state. Weather memory is cleared and late weather writes are ignored.

Explicit deletion failures are reported and the in-memory roster is hidden. If browser storage itself refuses deletion, the user must clear website data in browser settings; the app does not claim physical deletion succeeded.

Local storage is not encrypted. Same-origin malicious scripts or someone with access to the unlocked browser can access locally stored information. Offline revocation cannot be checked remotely. Cache age and coverage remain visible, and out-of-coverage days remain unknown.

## Remaining limitations

- Physical iPhone/Home Screen acceptance remains outstanding.
- **Service-worker update latency:** there is deliberately no `skipWaiting`; a new version activates only after every client of the old one has closed. An installed iPhone Home Screen app is rarely fully closed, so after a deploy it can keep serving the previous shell for a long time. Release checklist: after a deploy, force-close the Home Screen app (and other tabs) and confirm the new version; a user-visible "update available" prompt is future work.
- Browser data eviction, manual site-data deletion and private-mode restrictions can remove or prevent offline storage. Persistent-storage requests are not guarantees.
- Safari and an installed Home Screen app must be treated as potentially separate storage contexts; synchronize inside the installed app.
- Live weather, departures refresh and external map/hotel links need connectivity. Their failure must not block roster screens.
- A genuinely completely empty roster has no affirmative source signal distinguishing it from an incomplete response. Preserve the last good copy and show refresh failure; explicit reset clears it if desired. Explicit OFF/leave/standby rosters are accepted. **Known limitation, must be resolved before multi-user onboarding** (a new user with an empty roster would see a permanent refresh failure); it needs a source-stated "roster published, no events" signal in the contract.
- All retained information is the last known roster within its recorded coverage, not proof of operational changes that happened while offline.
- Service-worker updates wait until old clients close, intentionally avoiding mixed-version files.

## Independent-review remediation decisions

All two high, four medium and four low findings have been addressed. No backend, production resource, source contract, Local/UTC calculation or duty-state semantics changed. `npm run build` and `npm run check` alias the existing offline commands.

- Point events: permit equality and count point events on their source-local coverage day, including midnight; reject reverse intervals.
- v5 recovery: apply the no-downgrade restriction only to a genuinely saved v2 record.
- Authentication policy changes: revoke open/no-token saved data on confirmed authentication-required responses; retain configured-token offline access.
- Cache misses: recover verified identical bytes from the previous shell or network, otherwise serve network-only bytes without caching or claiming readiness.
- History: retain good history while recording daily checks even when empty or partially adaptable.
- Manual refresh: provide an existing-style quiet button in Settings that bypasses only the online hint, not authentication or validation.
- Low findings: document HTTPS and return a secure-context error; compute Disconnect status after removing the endpoint; queue one retry for a failed request interrupted by reconnect; use stale styling for offline data, remove obsolete status logic, reuse the render view, and share storage constants.

Re-saving a source or credential continues to reset its device history. This conservative isolation behavior is intentional in Step 6.6; preserving history across credential changes would need a separately designed account-identity guarantee. Existing protected-preview preparation artifacts must be regenerated from this reviewed source before any later approved deployment. No preview artifacts were deployed or remote projects changed by remediation.

| H2: v5 recovery blocked | A saved record of either contract enabled the v2-only recovery restriction. | Gate the restriction on the saved contract being v2. Test repeated v5 fallback followed by successful v2 recovery. |
| M3: open backend becomes protected | Cleanup required there to be no saved record, excluding precisely the sensitive cache that needed revocation. | Purge saved/open data, set the persistent revocation marker and invalidate access for other tabs and late requests. | M4: missing static asset fails online | Recovery enforced the old hash by rejecting the network response; retained prior caches were never read. | Read a previous entry only after matching the active hash. ## Step 6.6 addition: mobile pull-to-refresh

Today, Calendar and Flights (including flight details) expose a visible, keyboard-operable Refresh button and a scoped single-touch pull gesture. The gesture must start at document scroll position zero, away from the left/right 24px navigation edges, controls and nested vertical scrollers. It locks only after clear downward intent (more than 12px, predominantly vertical) and requires 80px total travel on release. Retreating below threshold, horizontal/upward motion, multitouch, touch cancellation or navigating to a different screen disarms it.

Only a claimed vertical pull calls `preventDefault`, to avoid the browser also reloading the document. There is no global `touch-action` or overscroll override, page translation or interference with unclaimed scrolling/navigation gestures. A non-cancelable gesture is abandoned rather than competing with a gesture already owned by the browser. Real iOS rubber-banding and browser navigation still require physical acceptance.

All entry points use `controller.refresh({ force: true })`, including when `navigator.onLine` is false. Local gesture/button and controller guards prevent duplicate requests. Existing cached roster content stays visible and retains its existing failure protections. The control survives data-driven rerenders; focus stays on the fallback button, and an accessible live status announces pulling, release and refreshing states without repeating unchanged text on every movement. Reduced-motion preference disables rotation; text feedback remains.

New files: `src/ui/pull-refresh.js`, `tests/pull-refresh.test.js`. Updated: `src/main.js`, `assets/css/shell.css`, `tests/browser/offline.mjs`, generated `sw.js`, and this document. No backend or deployed resource changes.

Additional physical-iPhone acceptance: on each of Today, Calendar and Flights, test short/long pulls, retreat before release, normal upward/downward scrolling when below the top, horizontal calendar gestures, edge navigation, interactive controls and a second finger. Confirm exactly one refresh and no page reload for a deliberate top pull. Hold a synthetic response to confirm content remains visible and repeated pulls/button taps do not duplicate it. Test airplane mode failure, stale online indication, VoiceOver/button activation and Reduce Motion. Repeat in both Safari and the installed Home Screen app.

Pull-to-refresh verification: `npm run build`, `npm run check`, and `git diff --check` passed. Full regression suite: **763 passed, zero failures**, including three new gesture/control tests. The cookie-protected, touch-enabled 390×844 Chrome harness passed all existing offline/authentication checks plus real dispatched touch pulls on all three screens, below-top/short/horizontal rejection, stale `navigator.onLine` handling, no document navigation, in-flight deduplication, malformed-response cache preservation, keyboard focus retention and reduced-motion CSS. ## Emergency rollback (prepared 2026-10-15, never activated)

Once a device has the Step 6.6 service worker, reverting `main` alone is **not** a rollback: the installed
worker keeps serving its cached shell. The rollback artifact is `scripts/rollback/sw.js`, a self-removing
worker. It is not part of the normal build, so it is never precached and never deployed by accident.

What it does, once a browser fetches it as the app's `sw.js`:
1. Activates at once (`skipWaiting`).
2. Deletes only caches whose names start with `fc-shell-`. Other caches on the shared GitHub Pages
   origin, such as the `roadmap` site, are kept.
3. Unregisters only its own registration (scope `/flight-control/`).
4. Reloads its open windows, which then load the restored application from the network.

It has no fetch handler and never touches `localStorage`, IndexedDB or cookies. The saved roster, the access
token, the endpoint and all settings survive. The restored pre-6.6 app (`0ae7d58`) uses the same `token.v2` and
`endpoint` keys and reconnects. It has no offline copy and no device history of its own: the 6.6 migration
deleted the legacy cache keys.

**Activation (owner approval required at every step):**
1. Choose the restore target `R` (the last good release, e.g. `0ae7d58`).
2. `git switch -c rollback/<date> origin/main && git revert --no-commit R..origin/main`
3. `git show <release-commit>:scripts/rollback/sw.js > sw.js && git add sw.js && git commit -m "rollback: restore R, retire offline shell"`
4. Verify locally before deploying: `PLAYWRIGHT_MODULE_PATH=… node tests/browser/rollback-subpath.mjs R`. The test
   restores the tree of `R` with the rollback worker served as `sw.js`.
5. Fast-forward `main` to the rollback branch. GitHub Pages deploys it.
6. Leave the rollback `sw.js` deployed until every device has updated (suggested ≥ 30 days). Never delete it
   while 6.6 shells may still be installed. A later re-release replaces it with a new generated `sw.js`.

**Limitation (verified in desktop Chrome; iPhone not yet tested):** the rollback reaches a device only through the
browser's own service-worker lifecycle:
1. *Update check:* the browser must fetch the new `sw.js`. Chrome usually does this on launch. Browsers promise a
   check at least every 24 h on navigation.
2. *Activation:* in a final run of 30 (desktop Chrome, `/flight-control/`), 28 completed on the first launch. In 2,
   the rollback worker installed but stayed **waiting**, despite `skipWaiting()` and three explicit
   `registration.update()` calls, while the old shell still controlled the open page. **One relaunch** (all
   pages closed, app reopened) completed the rollback in both. Earlier runs, before the harness fixes, showed the
   same pattern once without an update check.

Practical rule for an emergency: after deploying the rollback, **force-close and reopen** the Home Screen app,
and do it again if the old version still shows. The harness models exactly this: launch, up to 3 update calls,
then up to 2 relaunches. A rollback that a relaunch cannot complete fails the test. The 6.6 shell does not call
`update()` itself; adding that on launch and on foregrounding (I-006) would shorten step 1, but it would not remove
the waiting case.

**Verification:** `tests/rollback-worker.test.js` (unit, part of `npm test`) and `tests/browser/rollback-subpath.mjs`
(desktop Chrome, served under `/flight-control/`, synthetic data). The browser test covers:
- the subpath: startup, asset loading, worker registration and scope, manifest `start_url`/scope, offline
  startup and navigation, cached roster;
- the rollback: an installed 6.6 shell with a full cache; same-origin neighbour app and caches; rollback
  deployed; shell caches and registration removed; neighbours, roster, token and settings intact; the
  restored `0ae7d58` app loads from the network and shows its roster; no worker re-registered.
